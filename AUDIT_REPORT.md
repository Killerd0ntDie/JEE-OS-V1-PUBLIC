# JEE OS — Comprehensive Audit Report (v2)

## 1. Security & Hygiene Assessment

> [!CAUTION]
> **Critical Findings**
> - **Live Credential Leak:** The `.env` file contains a live-looking `FIREBASE_SERVICE_ACCOUNT_KEY` JSON string and `.env.local` contains a `GEMINI_API_KEY`. While gitignored, `server/firebaseAdmin.ts` uses `process.env.FIREBASE_SERVICE_ACCOUNT_KEY` directly via `JSON.parse` to bypass auth in non-production, which is a major credential management risk.
> - **Overly Permissive Firestore Rules:** The `firestore.rules` file allows `allow read, write: if true;` for `pyq_bank`, meaning any unauthenticated user can read or modify the PYQ database (Lines 9-10).

> [!WARNING]
> **High Findings**
> - **Typescript Compilation Fails:** The `M4: Final Build & E2E Verification... npm run build zero errors` claim in `.agents/orchestrator/PROJECT.md` is **FALSE**. Running `npx tsc --noEmit` fails with 6 errors inside `server/firebaseAdmin.ts` (e.g., `Property 'apps' does not exist on type 'typeof admin'`).
> - **Test Suite Failures:** The `npx vitest run` command fails on `src/engines/planner/PlannerEngine.test.ts`. Specifically, a test fails with `AssertionError: 105 expected to be 90` related to study duration logic.

## 2. Architecture & State Management

> [!WARNING]
> **High Findings - Architectural Drift**
> - **Parallel State Engines (Two Sources of Truth):** The `ChapterInfoEngine` was introduced to act as a centralized telemetry source (`chapterTelemetryMap`). However, `PlannerEngine`, `OptimizationEngine`, and `AnalyticsEngine` still compute their own versions of mastery, syllabus stage, and revision decay using the old `getAcademicState` utility and manual logic. This creates a severe risk of conflicting data across the app.
> - **AI Coach Prompt Leak:** In `server.ts` line 121, the backend returns raw `response.text` directly to the client (`res.json({ analysis: response.text })`) without sanitizing `<think>` blocks or stripping out markdown reasoning tags that might be generated by the Gemini model.

> [!IMPORTANT]
> **Medium Findings**
> - **Dual State Stores:** The application maintains both `StudyBrainContext.tsx` and `useStudyBrainStore.ts` (Zustand), leading to a split brain in state management. The `StudyBrainRuntime` attempts to sync these, but the architecture is disjointed.

## 3. UI & Modal Portal Verification

> [!IMPORTANT]
> **Medium Findings - False Completion Claims**
> - **Incomplete Modal Portal Migration:** The previous claim that "all 12 modal components use ModalPortal and useLockBodyScroll" is **FALSE**. While 9 components (e.g., `ChapterEditModal`, `AiPracticeModal`, `WeeklyCheckinModal`) were successfully migrated to use `ModalPortal`, several others still render directly in the DOM tree with `fixed inset-0 z-[100]`. Examples include:
>   - `CustomMissionModal.tsx`
>   - `MissionCalibrationModal.tsx`
>   - `MissionCompleteModal.tsx`
>   - `LogMistakeModal.tsx`
>   - `BatchReviewModal.tsx`
>   - `FeynmanSandboxModal.tsx`
>   - `FormulaSpeedDrillModal.tsx`
>
> These modals remain vulnerable to z-index and portal scrolling bugs.

## 4. AI Coach Architecture Verification

> [!NOTE]
> **Verified Components**
> - **Universal ChapterEditModal:** Verified that `ChapterEditModal` is centralized in `App.tsx` and triggered globally via `actions.openChapterEditModal()`. It is successfully integrated across `DailyMissionTimeline`, `PlannerPage`, `AnalyticsPage`, and `ChapterRevisionInspectorModal`.
> - **Cache Invalidation:** The reviewer identified a cache invalidation bug in `ChapterInfoEngine` (hashing `mistakes.length`). This was actually fixed by the worker; `computeInputHash` now hashes `m.revisionStatus` and `m.status`.

## 5. Verification Process Summary
This audit was performed strictly through non-destructive verification:
1. `npm install` and `npx tsc --noEmit` were executed to verify build claims.
2. `npx vitest run` was executed to verify test suite health.
3. Code reviews of `server/firebaseAdmin.ts`, `server.ts`, and `.env` were conducted to locate secrets and logic leaks.
4. Search queries were run across `src/features` and `src/components` to identify actual `ModalPortal` implementations versus direct `fixed` styling.
